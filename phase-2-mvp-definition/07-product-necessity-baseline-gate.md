# ReadMatch 产品必要性与通用大模型 Baseline 验证门

形成日期：2026-08-10
所有权：用户主导产品判断，助手提供实验设计和分析支持
状态：开发前必要性验证；时间盒 1—2 天，不进入完整编码

## 一、为什么增加这一道验证门

项目负责人在 PRD 学习检查中提出核心质疑：

> 如果用户直接询问带联网能力的通用大模型也能得到答案，ReadMatch 是否只是多此一举？

这是当前项目最重要的产品问题。通用大模型已经能够搜索网络、整合多个来源并提供引用，因此“搜索一本到书并总结信息”本身不足以成为独立产品价值。

在投入 MVP 编码前，必须验证 ReadMatch 的受控证据工作流是否在一个具体任务上产生稳定、可测量的优势。如果没有优势，应该调整产品，而不是为了作品集继续开发。

## 二、纠正产品定义

### 不采用

> 精确检索推荐小说阅读的软件。

问题：同时包含搜索、推荐和阅读，范围不清；“精确”没有指标；与通用大模型搜索和阅读平台功能重叠。

### 当前待验证定义

> ReadMatch 是一个用户可控的小说阅读风险决策助手。它将用户的硬性雷点和本次偏好转成一份可执行的核验清单，对一本到已收录候选书逐项检查，并区分基础事实、读者观点、冲突证据和未知项，帮助用户决定试读、排除或继续核验。

### 核心任务

不是“替用户查资料”，而是：

```text
把用户的个人边界变成检查清单
→ 保证每个硬性雷点被检查
→ 给出可追溯证据
→ 对证据不足诚实标记未知
→ 形成可执行决定
```

## 三、ReadMatch 可能产生的相对优势

1. **完整检查**：每个用户选择的硬性雷点都必须返回状态；
2. **证据归属**：所有结论必须引用当前作品的 evidence_id；
3. **观点分层**：事实、读者观点、AI 归纳和未知分开；
4. **冲突保留**：相反评价不被平均成一个绝对结论；
5. **未知校准**：没有检索到不等于不存在；
6. **稳定可复现**：同一评测 Case 可以做版本回归；
7. **反馈闭环**：事实错误、雷点遗漏和证据不一致进入 Bad Case；
8. **用户动作**：输出围绕试读、排除和继续核验，而不是长篇总结。

这些是待验证优势，不是已经证明的护城河。

## 四、必须接受的现实

如果把同一批高质量证据和规则 Prompt 提供给通用大模型，它也可能完成类似任务。因此 ReadMatch 的价值不来自“模型不可替代”，而来自：

```text
领域证据数据
+ 用户雷点结构
+ 固定工作流
+ 规则和质量门
+ 评测与反馈闭环
+ 更低的重复操作成本
```

任何大模型平台都可能模仿功能。项目目标不是证明技术无法复制，而是证明在特定用户任务上，这套产品化工作流比默认聊天更稳定、更省心、更可控。

## 五、1—2 天必要性实验

### 实验对象

由项目负责人选择 5 本自己熟悉、公开讨论较多且评价存在差异的纯爱小说。

每本设置 2 种用户偏好，共 10 个 Case：

- 1 个正常匹配/偏好 Case；
- 1 个包含硬性雷点或证据不足的 Case。

### 方案 A：默认通用大模型

输入：

```text
书名 + 用户偏好/雷点
```

让模型按自然方式回答，不提供 ReadMatch 证据包。

### 方案 B：优化后的通用大模型 Prompt

输入相同，但要求：

- 区分事实和观点；
- 提供来源；
- 标记未知；
- 检查所有雷点。

该方案代表“用户会写好 Prompt”的强 Baseline，不能只和最弱的大模型回答比较。

### 方案 C：ReadMatch 手工模拟

不先写代码，使用：

- 受控作品事实；
- 编号证据包；
- 硬性雷点清单；
- 固定输出结构；
- 规则检查。

人工执行当前 PRD Workflow，模拟未来产品结果。

## 六、比较指标

| 指标 | 含义 |
|---|---|
| 基础事实正确率 | 书名、作者、状态等是否正确 |
| 结论证据支持率 | 匹配和风险是否有来源支持 |
| 硬性雷点覆盖率 | 用户选择的雷点是否逐项检查 |
| 无证据确定性结论 | 是否把未知写成不存在 |
| 冲突观点保留 | 是否展示相反评价 |
| 决策可执行性 | 用户是否能选择试读、排除或继续核验 |
| 完成时间 | 获得可用结论所需时间 |
| 用户操作负担 | 用户需要多少追问、核验和 Prompt 调整 |

## 七、继续开发的判断标准

10 个 Case 只用于方向性判断，不做总体统计推断。

满足以下多数条件时继续当前 ReadMatch 路线：

- 方案 C 明显减少 P0 错误；
- 方案 C 的雷点覆盖和未知表达更稳定；
- 优化 Prompt 的方案 B 仍需要用户多次追问或人工核验；
- 至少 4/5 测试用户认为方案 C 更容易形成决定；
- ReadMatch 的新增流程成本没有抵消其准确和可信优势。

## 八、需要调整或转向的信号

- 方案 B 与方案 C 在关键指标上基本相同；
- 用户不使用证据、雷点状态和未知项；
- 用户只想要一个简短聊天答案；
- 构建证据包的人力成本远高于用户获得的价值；
- 大多数用户搜索的作品无法覆盖；
- 用户不愿完成任何偏好或雷点输入。

## 九、如果当前方案不成立的三种方向

### 方向 1：个人阅读偏好模型

从一次性判断转向可编辑、可积累的结构化个人偏好档案，再用于多本作品比较。

### 方向 2：用户/运营提供证据的分析器

不依赖大规模预置书库，由用户或内容运营人员提供证据包，系统负责结构化、冲突归纳和风险检查。

### 方向 3：内容运营/书单生产工具

服务书单作者、社区运营或编辑，帮助批量生成可审核的作品画像和避雷卡。

是否转向必须由实验和数据决定，不在当前提前冻结。

## 十、当前项目负责人回答复盘

### 首次定义

> 是一个精确检索推荐小说阅读的软件，解决用户多平台找寻小说信息的复杂度，降低时间成本。

### 需要修正

- 产品不是阅读软件；
- 第一版不是多本推荐系统；
- “精确”必须拆成事实、证据、雷点和未知指标；
- 核心价值不仅是减少搜索时间，而是降低做出错误阅读决定的风险。

### 当前建议表达

> ReadMatch 是一个用户可控的小说阅读风险决策助手。它针对用户已经找到的一本候选作品，逐项核验个人偏好和硬性雷点，展示可追溯证据、冲突观点和未知项，帮助用户减少跨平台核验并做出试读、排除或继续确认的决定。

## 十一、下一步用户必须完成

1. 选择 5 本用于必要性实验的纯爱小说；
2. 每本写出一个你认为常见的正向需求；
3. 每本写出一个硬性雷点或证据不足场景；
4. 不需要先收集完整证据，助手将提供 Case 模板并协助建立证据包；
5. 实验结束前不宣称 ReadMatch 相比通用大模型更好。
