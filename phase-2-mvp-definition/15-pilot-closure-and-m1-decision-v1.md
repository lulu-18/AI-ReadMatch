# ReadMatch 预测试关闭与 M1 启动决定 v1

形成日期：2026-08-11
所有权：双方共创，项目负责人确认方案 C 可接受
状态：预测试关闭；允许进入最小端到端 Demo

## 一、关闭理由

两条预测试已经完成：

- 统一输入；
- 默认通用大模型 Baseline；
- 优化 Prompt Baseline；
- ReadMatch 受控证据手工模拟；
- 事实、证据、雷点、未知、剧透、动作和时间评分；
- 项目负责人初步可用性复核。

## 二、方向性结果

- 简单、官方信息充分的条件上，优化 Prompt 已能接近 ReadMatch；
- 复杂雷点、定义歧义、来源冲突和重大剧透场景中，通用大模型仍出现可测量问题；
- 优化 Prompt 平均等待时间约为普通提问的 7.22 倍；
- ReadMatch 的潜在增量是把证据等级、雷点逐项检查、未知、剧透和简短行动建议固化为产品能力；
- 用户不需要每次自己编写复杂 Prompt 或阅读数千字回答。

## 三、产品定义调整

PRD 核心定义不推翻，但价值表达进一步聚焦：

> ReadMatch 是面向对雷点、来源和剧透敏感的纯爱读者的阅读风险决策助手。它把用户边界转换为逐项核验清单，基于受控证据输出匹配、风险、冲突和未知，并以较短、稳定、可回归评测的方式帮助用户决定试读、排除或继续核验。

## 四、为什么不立即手工运行剩余 8 个 Case

如果继续手工测试：

- 需要额外 16 个独立对话；
- 优化 Prompt 单次已需要约 2—3.5 分钟；
- 原始输出长，人工复制和评分成本高；
- 后续实现 API 和评测脚本后可以批量运行、保存原始输出和自动统计。

因此调整顺序：

```text
两条预测试通过
→ M1 三本样例端到端 Demo
→ 自动评测脚本
→ 批量执行完整 10 Case
→ 根据结果决定是否扩展到 30 本
```

这不是跳过验证，而是把剩余验证放到更可复现的工程阶段。

## 五、M1 建议样例作品

1. 《撒野》：官方事实清楚、多条件检查；
2. 《囚于永夜》：ABO、复合伤害、领域词和剧透；
3. 《魔道祖师》：古风/前世今生/人物观点与感情线速度，用于增加题材和程度型标签差异。
