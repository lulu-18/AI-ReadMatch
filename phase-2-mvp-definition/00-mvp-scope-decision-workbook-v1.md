## 决策 1：一个月项目的最终交付目标

### 助手建议

一个可运行、可评测、可演示的 Web MVP，能够：

1. 接收用户的喜欢作品、偏好和硬性雷点；
2. 从受控的小型真实书库召回候选；
3. 基于编号证据生成匹配点、风险和未知项；
4. 输出 3 本候选；
5. 接收试读、排除、理由不准和雷点遗漏反馈；
6. 提供完整评测报告和项目复盘。

### 项目负责人必须回答

- 你认为一个月后，什么结果才算项目成功？
- Demo、评测报告、用户数据和作品集中，哪一个最重要？为什么？
- 如果时间不够，你最不能放弃的产物是什么？

### 项目负责人最终决定

**用户原始决定：**

- 一个月内完成完整的项目开发流程，并包含测试和优化；
- 项目负责人需要对项目有非常深入的理解；
- 产出优先级：求职作品集和面试表达 > 评测和迭代数据 > 可运行 Demo > 用户真实反馈；
- 最不能放弃的是与面试必答题相关的核心决策、证据和复盘材料。

**产品评审后的正式表述：**

本项目的第一目标是形成一套项目负责人能够独立讲解和接受深挖的 AI 产品项目证据链；第二目标是完成有评测、有迭代的可运行 MVP。用户真实反馈不作为规模化目标，但仍保留最低 5 次真实测试，用于避免项目只在内部自证。

**必须交付：**

1. 产品问题、用户和 MVP 取舍记录；
2. PRD v1 与 AI 系统架构；
3. 可运行 Demo；
4. 评测集、评测结果和至少两轮优化记录；
5. 至少 20 个由项目负责人亲自审核的 Bad Case；
6. 最少 5 次真实用户测试；
7. 作品集、演示视频、简历描述和面试问题库；
8. 项目负责人能够脱离文稿解释所有关键决定。
## 决策 2：第一版核心场景

### 选项 A：从书库直接推荐

用户输入偏好，ReadMatch 从书库推荐 3 本。

优点：完整体现推荐产品。

风险：同时需要解决召回、排序和解释，范围更大。

### 选项 B：帮助判断用户已有候选

用户输入 1—3 本候选，ReadMatch 帮助分析匹配点和雷点。

优点：更聚焦证据理解和避雷，更容易做好。

风险：不能完整展示候选召回能力。

### 选项 C：两步组合

用户可以输入已有候选；没有候选时从小型书库推荐 3 本。两种入口共用同一套书籍画像和证据系统。

优点：项目故事完整。

风险：一个月范围可能偏大。

### 助手当前建议

以 B 为第一条必须跑通的核心链路，以 A 作为第二优先级；不要第一天同时开发两个入口。

原因：现有研究最强的证据是“候选后的二次筛选和跨平台核验成本”，而不是用户完全缺少候选书名。

### 项目负责人必须回答

- 你认为 ReadMatch 最重要的是“帮我找到书”还是“帮我判断一本书”？
- 如果只能保留一个入口，你选择哪个？
- 这个选择如何对应问卷和竞品证据？

### 项目负责人最终决定

**用户原始决定：**

选择方案 B：帮助用户判断一本书。原因是范围更简单，更适合单人开发项目。

**产品评审后的正式表述：**

第一版核心场景冻结为“单本候选决策”：用户已经知道一本小说，在开始阅读前输入书名和个人偏好/雷点，ReadMatch 基于受控证据判断这本书与用户的匹配点、可能风险和未知项，并支持用户做出“愿意试读、排除、继续核验”的决定。

第一版不负责从零生成大量候选书名。后续版本可以在同一书籍画像和证据系统上增加书库推荐入口。

**范围价值：**

- 与当前最强研究证据一致：问题主要发生在获得候选以后；
- AI 任务更聚焦于内容理解、证据归纳、个性化比较和不确定性表达；
- 适合一个月内完成数据、评测、MVP 和迭代闭环；
- 更容易解释为什么不用复杂推荐算法或多 Agent。
## 决策 3：首批细分题材

### 现有证据

31 份问卷中，多选偏好较高的方向包括：

- 穿书、重生、系统等设定：15；
- 现代言情：14；
- 纯爱/耽美：11；
- 娱乐圈、职场、校园等背景：9；
- 现言甜宠：9；
- 古言：8。

这只能说明本批样本覆盖，不能自动决定产品范围。

### 助手当前建议

优先考虑“现代言情/现言设定向”，可包含穿书、重生、系统、校园或职场等背景，但仍需考虑项目负责人最熟悉、最容易获得真实书籍和评价证据的方向。

### 项目负责人必须回答

- 你最熟悉、能够判断雷点和文风的题材是什么？
- 哪个题材最容易获得 30—50 本真实作品和可追溯证据？
- 你希望面试时展示的是言情推荐、女频内容理解，还是更广义的小说决策系统？

### 项目负责人最终决定

**用户原始决定：**

首批选择纯爱/耽美题材，因为项目负责人在该方向涉猎较深；对外将项目定位为小说决策系统。

**产品评审后的正式表述：**

MVP 首批垂直内容范围冻结为纯爱/耽美小说。项目整体定位为“基于证据的个性化小说决策系统”，纯爱/耽美是第一批验证领域，而不是永久限制。

**定位表达：**

- 用户层：帮助纯爱读者在开始一本候选小说前判断是否适合自己；
- 产品层：整合基础事实、读者观点、个性化偏好、可能雷点和未知项；
- AI 层：验证大模型对主观内容观点的结构化提取、证据归纳和个性化匹配能力；
- 扩展层：如果验证有效，同一套 Schema、评测和工作流可以扩展到其他小说题材。

项目负责人对该领域有较深阅读经验，这有利于数据审核和 Bad Case 判断；但个人经验不能替代可追溯证据，书籍画像仍需保留来源和未知项。
## 决策 4：最低用户输入

### 助手建议的 P0 输入

- 喜欢过的 1—3 本书；
- 每本喜欢或不喜欢的简短原因；
- 2—5 个希望满足的条件；
- 2—5 个明确不能接受的雷点；
- 可选：当前想判断的候选书。

不要求：

- 社交账号；
- 私人笔记；
- 完整阅读记录；
- 未打码截图；
- 长期偏好画像。

### 项目负责人必须回答

- 用户必须提供什么，系统才能产生有效结果？
- 哪些输入虽然有价值，但第一版不应该强制？
- 输入多少内容会让你自己放弃使用？

### 项目负责人最终决定

**用户原始决定：**

选择方案 C：自然语言偏好 + 单独填写硬性雷点 + 可选参考作品。但用户输入应以选项为主，减少自然语言输入，避免用户因为不耐烦或临时想不起偏好而放弃使用。

**产品评审后的正式表述：**

第一版采用“结构化选项优先 + 自然语言补充”的混合输入，而不是以长文本为主要入口。

**P0 必填：**

1. 候选书名；
2. 希望满足的偏好选项，可多选；
3. 绝对不能接受的硬性雷点，可多选。

**P0 选项建议分组：**

- 人物：双强、成长型、理智、非降智等；
- 关系：强强、年上/年下、破镜重圆、先婚后爱、相爱相杀等；
- 感情线：拉扯感、甜度、慢热、感情占比；
- 剧情与节奏：剧情向、感情向、节奏快、允许慢热；
- 文风：轻松、细腻、幽默、正剧、强情绪；
- 结局与状态：HE/BE、完结/连载；
- 硬性雷点：长期误会、人物降智、过度虐恋、强制控制、出轨背叛、烂尾、重要角色死亡等。

**P0 交互规则：**

- 提供“没有明确偏好”“暂时想不起来”“其他”选项；
- 普通偏好和硬性雷点必须分开；
- 用户可以只选 1—3 个关键条件，不强迫建立完整画像；
- 系统在分析前展示结构化结果供用户确认或修改。

**可选输入：**

- 一句话补充偏好；
- 喜欢的参考作品及原因；
- 不喜欢的参考作品及原因；
- 选项中没有覆盖的自定义雷点。

**风险控制：**

选项可以降低输入成本，但也会限制用户表达并产生标签诱导。因此必须保留“其他/补充说明”，并通过后续用户反馈检查选项是否遗漏常见偏好。
## 决策 5：第一版输出

### 助手建议的 P0 输出

每个候选显示：

- 书名、作者、来源平台和完结状态；
- 匹配点；
- 可能不适合的地方；
- 硬性雷点检查；
- 证据编号和来源类型；
- 相反评价；
- 证据强度；
- 当前未知；
- 建议动作：试读、排除或继续核验。

### 项目负责人必须回答

- 用户看完结果后，最重要的动作是什么？
- 哪三个字段必须第一眼看到？
- 哪些字段可以折叠？
- 系统是否应该直接给出结论，还是只提供证据？为什么？

### 项目负责人最终决定

**用户原始决定：**

接受助手建议的输出结构，并明确要求必须提供用户反馈选项，用于后续产品优化。

**产品评审后的正式表述：**

第一版输出采用“结论摘要 + 匹配/风险/未知 + 证据 + 用户动作与反馈”的分层结构。

**第一屏 P0：**

1. 综合判断：可能适合 / 可能不适合 / 证据不足；
2. 最重要的匹配点；
3. 最需要注意的风险；
4. 用户硬性雷点的检查结果；
5. 当前仍无法确认的条件；
6. 建议动作：愿意试读 / 排除 / 继续核验。

**展开后 P0：**

- 书名、作者、来源平台和完结状态；
- 具体匹配分析；
- 可能雷点；
- 相反读者评价；
- 证据编号和来源类型；
- 证据强度；
- 未知项；
- 剧透等级和主动展开。

**用户反馈 P0：**

- 判断基本准确；
- 匹配点不准确；
- 雷点判断错误或夸大；
- 遗漏了我的硬性雷点；
- 书名、作者或状态错误；
- 证据与结论不一致；
- 未知项太多；
- 出现不希望看到的剧透；
- 其他补充。

**产品行为反馈：**

- 愿意试读；
- 排除；
- 继续核验。

**反馈使用原则：**

- 用户反馈用于发现 Bad Case、优化标签、Prompt、证据和产品流程；
- 单个用户的主观反馈不能自动覆盖书籍事实或成为全体用户结论；
- 事实错误、硬性雷点遗漏和证据不一致属于高优先级问题；
- “不喜欢”不一定代表系统错误，需要区分个性偏好与事实错误。
## 决策 6：AI 的必要性

### 助手建议

AI 第一版主要负责：

- 从自然语言偏好中提取结构化条件；
- 从书评证据中提取文风、节奏、人物、关系和雷点观点；
- 合并重复观点并保留冲突；
- 比较用户偏好与书籍画像；
- 基于证据生成解释；
- 证据不足时输出未知。

规则系统负责：

- 限制只能输出书库中的真实书籍；
- 核对书名、作者和完结状态；
- 处理硬性雷点过滤；
- 检查每条结论是否有证据编号；
- JSON 校验和失败回退。

### 项目负责人必须回答

- 如果完全不用大模型，哪些步骤最难实现？
- 哪些步骤必须由规则系统控制，不能交给大模型自由判断？
- 为什么第一版不用 Agent？
- 什么错误是可以接受的，什么错误绝对不能接受？

### 项目负责人最终决定

**用户原始决定：**

1. AI 主要负责数据归纳、整理和输出；
2. 输出必须基于事实，不能由 AI 无约束决定；
3. 选择方案 B，因为可以连接数据库、检索、大模型和规则等多方面能力；
4. 不选择大模型直接回答，因为回答容易过于绝对，评测难度大；
5. 不选择全部标签和规则，因为人工维护成本大，没有充分利用 AI 能力；
6. 最担心编造谎言、系统不安全和用户失去信任；
7. 证据不足时展示有限已知信息并标记未知；
8. 当前还不能解释为什么第一版不需要 Agent，需要继续学习。

**产品评审后的正式表述：**

第一版选择“受控数据库 + 证据检索 + 大模型归纳 + 规则校验”的固定工作流。

**大模型负责：**

- 理解书评等非结构化文本；
- 将不同表达归一为人物、关系、文风、节奏和雷点等结构化观点；
- 合并重复观点并保留相反评价；
- 比较用户偏好与书籍证据；
- 基于检索到的证据生成个性化解释；
- 证据不足时整理有限已知信息和未知项。

**数据库和规则负责：**

- 书名、作者、平台、完结状态等基础事实；
- 限制系统只能分析受控书库中的作品；
- 硬性雷点检查；
- 证据编号与作品身份一致性；
- 禁止无证据的确定性结论；
- JSON Schema 校验；
- 剧透控制和失败回退。

**为什么不用纯大模型回答：**

模型可能依赖不完整或错误的内部知识，容易产生过度确定、事实错误和无来源结论，也难以稳定复现和评测。

**为什么不用纯标签规则：**

纯规则需要大量人工定义和维护标签，难以理解书评中的隐含、主观和冲突表达，也无法充分利用大模型的语义理解和归纳能力。

**P0 严重错误：**

1. 分析一本到书时引用了另一本到书的证据；
2. 输出没有证据支持的事实或雷点结论；
3. 遗漏用户明确设置的硬性雷点；
4. 编造书名、作者、情节或来源；
5. 未经用户主动操作展示关键剧透。

“系统不安全”和“用户不信任”是这些错误造成的后果，不是可以直接评测的错误类型。后续评测需要统计具体错误事件。

**证据不足处理：**

优先展示已确认的有限信息，明确标记未知，并提供继续核验或谨慎试读的建议；不得为了给出完整答案而编造结论。

**Workflow 与 Agent 学习检查：已通过。**

项目负责人回答：

1. Workflow 需要提前设计好步骤，Agent 由大模型在执行过程中自行决定下一步；
2. ReadMatch v1 的程序链路固定，按照输入、检索、归纳和输出执行，不需要模型自主规划任务；
3. 强行加入 Agent 会增加系统复杂度、错误风险和调用成本；
4. 未来如果需要到多个外部网站自主检索、判断信息是否充分并决定下一步，才可能需要 Agent。

产品评审修正：固定 Workflow 不是“不需要模型思考”，而是不需要模型自主规划流程。大模型仍然负责在指定步骤中理解语义、归纳观点和比较偏好。Agent 也不一定必然降低准确率，但会扩大错误面、增加不确定性，并使评测和定位问题更困难。

## 决策 7：第一版评测指标

### 助手提出的候选指标

#### 模型质量

- 虚构书名或作者数量；
- 基础事实准确率；
- 观点提取准确率；
- 雷点识别准确率；
- 证据引用覆盖率；
- 未知项识别率；
- 硬性雷点违反率。

#### 系统质量

- JSON 输出成功率；
- 检索命中率；
- 平均响应时间；
- 单次调用成本；
- API 失败率。

#### 产品质量

- 用户能否完成试读/排除/继续核验决定；
- 推荐理由是否被采用；
- 用户纠错率；
- 雷点遗漏反馈率；
- 用户是否仍需跨平台核验。

### 项目负责人必须回答

- 第一版最重要的一个模型指标是什么？
- 最重要的一个产品指标是什么？
- 哪个错误一旦出现就不应该上线？
- 你愿意为了更高准确性牺牲多少响应速度或候选覆盖？

### 项目负责人最终决定

**用户原始决定：**

1. 第一版最重要的是结果准确，否则用户直接询问通用大模型即可，ReadMatch 没有独立价值；
2. 产品层最重视精准性；
3. 接受建立 30 条核心评测 Case，并亲自审核至少 20 条；
4. 接受比较“大模型直接回答”和“受控证据工作流”两种方案，但需要进一步理解 ReadMatch 的差异化；
5. 编造、引用错书、遗漏硬性雷点、无证据确定性结论、证据与结论相反、非主动关键剧透都属于不能接受的错误；
6. 准确性优先于响应速度，但响应不能过慢。

**产品评审后的正式表述：**

“准确”和“精准性”需要拆成可计算指标。ReadMatch v1 使用以下最小评测记分卡：

1. 基础事实正确率：目标 100%；
2. 结论证据支持率：目标不低于 95%，P0 结论目标 100%；
3. 已知硬性雷点召回率：核心评测集目标 100%；
4. 无证据确定性结论数：目标 0；
5. P0 严重错误数：最终核心评测集目标 0；
6. 用户决策帮助率：5 名测试用户中至少 4 名能够基于结果形成试读、排除或继续核验决定；
7. 平均响应时间：暂定不超过 10 秒，最终根据所选模型和真实测试调整；
8. 单次分析成本：必须记录，不在第一版先设绝对金额门槛。

**评测集：**

- 30 条核心 Case；
- 项目负责人亲自审核至少 20 条；
- 覆盖正常、硬性雷点、证据不足、观点冲突和对抗输入；
- 使用同一套 Case 对比直接回答 Baseline 与受控证据工作流。

**ReadMatch 相比直接询问通用大模型的待验证优势：**

- 只分析受控书库中的真实作品；
- 基础事实来自数据库而不是模型记忆；
- 每条匹配和风险结论可以追溯到证据；
- 对用户硬性雷点进行规则检查；
- 证据不足时稳定标记未知；
- 区分事实、读者观点和 AI 归纳；
- 收集结构化用户反馈并形成 Bad Case 闭环；
- 可以使用固定评测集持续回归验证。

这些优势目前是产品假设，不是已经证明的结果。如果受控工作流在同一评测集上没有明显优于直接回答 Baseline，就需要调整方案或重新评估产品价值，不能为了作品集隐瞒结果。

**决策 7 状态：已完成并冻结 v1，数值阈值允许在第一次 Baseline 评测后基于真实难度调整，但调整必须保留原因。**
## 决策 8：明确不做

### 助手建议

第一版明确不做：

- 全网自动抓取；
- 完整小说正文；
- 阅读器；
- 大规模作品库；
- 社交账号绑定；
- 自动长期用户画像；
- 多 Agent；
- 模型微调；
- 商业化和付费；
- 精细推荐排序算法；
- 所有言情/女频题材覆盖。

### 项目负责人必须回答

- 哪个不做项最容易让你忍不住扩大范围？
- 如果用户要求该功能，为什么第一版仍然不做？
- 哪个功能可以放到第二版，但需要提前预留数据结构？

### 项目负责人最终决定

第一版可以不做上述扩展功能，但后期可以根据验证结果和产品需要加入全网数据源接入、Agent 自主检索和多题材覆盖。扩展必须建立在 v1 的数据结构、证据规则、评测体系和固定 Workflow 已经稳定的基础上，不能因为“以后可能需要”而提前扩大 MVP。

**未来扩展原则：**

- 多题材覆盖：优先通过新增题材配置、标签和评测集扩展，不重写核心系统；
- 数据源接入：优先合法、稳定、可追溯的数据源，按数据源分别开发连接器，不把“全网抓取”作为一个简单开关；
- Agent：只有固定 Workflow 无法满足动态检索、工具选择和多轮核验时再引入；
- 每次扩展必须有独立目标、风险评估、评测集和退出标准。
